1 Introduction

1.1 Purpose

This Software Requirements Specification (SRS) outlines the functional and non-functional requirements for CampusMesh, a decentralized, multi-transport, delay-tolerant opportunistic peer-to-peer messaging system engineered for disconnected and intermittently connected campus environments. It details the operational scope, intended user classes, architectural boundaries, external interfaces, algorithmic models, and detailed system features. This document will serve as a formal reference for developers, testers, evaluators, and the course instructor in compliance with the IEEE 830 standard.

1.2 Document Conventions

This document follows the formatting and structural guidelines established by IEEE Std 830-1998:

  • Header: Font Size: 10 pt, Font Style: Bold Italic, Font: Times New Roman
  • Heading 1: Font Size: 20 pt, Font Style: Bold, Font: Times New Roman
  • Heading 2 / Sub Heading: Font Size: 15 pt, Font Style: Bold, Font: Times New Roman
  • Body Content: Font Size: 12 pt, Font Style: Regular, Font: Times New Roman, Line Spacing: 1.25
  • Requirements Identifiers: Numbered sequentially as FR-4.x.y for functional features and NFR-5.x.y for non-functional attributes.

1.3 Intended Audience and Reading Suggestions

This document is primarily intended for:

  • Campus End Users (Students, Faculty, Emergency Staff): Individuals utilizing the opportunistic mesh for offline messaging during internet blackouts. This section aids in understanding system capabilities and physical mobility reliance.
  • Academic Evaluator / Course Instructor (Prof. Yogita Patil): To assess whether the distributed systems architecture, algorithmic models, test coverage, and documentation align with IEEE standards and course expectations.
  • Developers and Maintainers: To clearly understand protocol state machines, buffer capacity constraints, socket serialization, and BLE GATT chunking procedures.
  • Network Testers: To design automated test cases validating message deduplication, token splitting, and multi-hop routing benchmarks.

This document is organized following the IEEE 830 structure. Readers are encouraged to review Sections 1 and 2 for conceptual grounding before diving into the formal technical requirements in Sections 3 through 6 and Appendices.

1.4 Product Scope

CampusMesh provides decentralized, infrastructure-free communication across university campuses by implementing the Store–Carry–Forward Delay-Tolerant Networking (DTN) model. Users can compose, buffer, and exchange priority-rated messages across heterogeneous devices (Windows, Ubuntu, Android, iOS) without requiring an active internet connection, cellular service, or centralized routing servers. By operating over both high-speed Wi-Fi sockets and short-range Bluetooth Low Energy (BLE) GATT channels, the system ensures that physical mobility bridges partitioned networks.

The platform features an autonomous peer discovery daemon, thread-safe memory-bounded local storage (10 MB cap), a dynamic routing engine supporting Epidemic, Spray-and-Wait, and Adaptive Multi-Metric Utility routing, length-prefixed TCP streaming, MTU-aware BLE packet slicing with CRC32 integrity verification, SQLite relational event logging, and an embedded zero-dependency HTTP REST control center featuring an interactive HTML5 canvas radar topology.

2 Overall Description

2.1 Product Perspective

In modern academic campus environments, everyday communications rely entirely on centralized infrastructure: cellular base stations, campus Wi-Fi access points, core switches, and cloud servers. During severe power failures, monsoon storms, network hardware breakdowns, or high-density campus events, centralized networks frequently collapse, creating total information dead zones. Traditional mobile messaging applications (WhatsApp, Telegram, Slack) fail completely without an active internet gateway.

CampusMesh is introduced to establish resilient, decentralized connectivity in such environments. Operating under the Delay-Tolerant Networking (DTN) store-carry-forward model, each device running CampusMesh functions as a standalone packet router and carrier. When two students or faculty members walk within radio range, their devices autonomously establish direct physical links over local Wi-Fi or Bluetooth Low Energy, exchanging stored messages before parting ways. Over time, messages cascade across the campus from student to student until reaching the target destination or diffusing across the entire community.

2.2 Product Functions

  • Autonomous zero-configuration discovery of neighboring peers via Wi-Fi mDNS, UDP subnet multicasting (239.255.77.88:5354), and BLE advertising.
  • Dynamic radio encounter detection and contact lifecycle tracking via ContactManager.
  • Store-Carry-Forward message buffering with strict 10 MB memory capacity enforcement.
  • Binary duplicate message detection and idempotent packet rejection.
  • Real-time timestamp-based Time-To-Live (TTL) tracking with automatic expiration purging.
  • Pluggable routing strategy selection: Epidemic Flooding, Spray-and-Wait binary token splitting, and Adaptive Utility scoring.
  • Multi-metric adaptive utility ranking balancing Priority ($P$), TTL Urgency ($T$), and Buffer Pressure ($B$).
  • High-speed stream-safe 4-byte big-endian length-prefixed TCP socket transport.
  • Bluetooth Low Energy MTU-aware slicing (23–512 bytes) with 13-byte headers and end-to-end CRC32 checksum reassembly.
  • Thread-safe relational event auditing to local SQLite database (database/campusmesh.db).
  • Embedded zero-dependency HTTP server delivering a real-time web control center on port 8080.
  • Interactive HTML5 Canvas radar displaying live node topology, multi-transport links, and animated packet hops.
  • Autonomous mobile device identification and independent client perspective switching.

2.5 Design and Implementation Constraints

  1. Zero External Web Frameworks: The backend control plane must execute using standard Java SE com.sun.net.httpserver.HttpServer with zero third-party dependencies (no Spring Boot, Tomcat, or Node.js runtime).
  2. Architectural Separation: The routing engine must decide what messages to forward, while transport sockets decide how messages are physically transmitted.
  3. Memory Capping: The message store is strictly bounded at 10 MB ($10,485,760$ bytes) to guarantee execution stability on low-resource mobile nodes.
  4. Intermittent Link Tolerance: Physical radios may disconnect at any moment during transit; all socket operations must timeout safely without corrupting buffered data.
  5. BLE MTU Slicing: Bluetooth Low Energy links must handle default 23-byte MTU boundaries up to 512-byte negotiated frames without losing chunks or overflowing buffers.
  6. Stateless REST Communication: The web dashboard must poll state via REST JSON endpoints without requiring persistent session cookies or client-side authentication.

  • Interactive Terminal CLI (interactive.bat): Built-in help menus and syntax instructions.
  • Automated Test Diagnostics: Real-time console test logs verifying 43 unit and functional test assertions.

2.7 Assumptions and Dependencies

  • It is assumed that devices physically move across campus, generating opportunistic radio encounters within 10–50 meters.
  • It is assumed that devices have either Wi-Fi or Bluetooth radios enabled.
  • It is assumed that device real-time clocks are reasonably synchronized for valid message TTL comparisons.
  • It is assumed that local file system write permissions exist for the SQLite database at database/campusmesh.db.

4 System Features

4.1 Autonomous Peer Discovery (Wi-Fi mDNS & Subnet UDP Beaconing)

4.1.1 Description and Priority

Enables zero-configuration proximity discovery across local Wi-Fi networks without requiring central directory infrastructure. Priority: High.

4.1.2 Stimulus/Response Sequences

  1. Node initializes DiscoveryManager on startup.
  2. WifiDiscoveryService binds to multicast address 239.255.77.88:5354.
  3. Background thread broadcasts JSON discovery beacons every 5 seconds.
  4. Neighboring nodes parse beacon metadata and update PeerRegistry.
  5. Nodes not heard from within 15 seconds are purged as stale.

4.1.3 Functional Requirements

  • FR-4.1.1: The system shall broadcast JSON UDP discovery beacons to 239.255.77.88:5354 every 5000 ms.
  • FR-4.1.2: The system shall parse inbound beacons and register peer ID, platform, IP address, port, and transports in PeerRegistry.
  • FR-4.1.3: The system shall evict peer entries whose last seen timestamp exceeds 15000 ms.

4.2 Opportunistic Bluetooth Low Energy (BLE) Radio Discovery

4.2.1 Description and Priority

Discovers adjacent physical nodes in complete Wi-Fi dead zones via BLE advertisements. Priority: High.

4.2.2 Stimulus/Response Sequences

  1. Node activates BLE peripheral service advertising UUID 0000FE60.
  2. Scanning nodes detect service and connect to GATT server.
  3. Scanning node reads Characteristic 0000FE61 to obtain peer identity.
  4. Peer is merged into PeerRegistry with transport capability BLE.

4.2.3 Functional Requirements

  • FR-4.2.1: The system shall broadcast BLE advertisements specifying Service UUID 0000FE60-0000-1000-8000-00805F9B34FB.
  • FR-4.2.2: The system shall query Characteristic 0000FE61 to ingest remote peer metadata.
  • FR-4.2.3: The system shall merge multi-transport capabilities into a unified peer record.

4.3 Store–Carry–Forward Message Buffer Management

4.3.1 Description and Priority

Maintains persistent in-memory message storage while nodes transit between network partitions. Priority: High.

4.3.2 Stimulus/Response Sequences

  1. Message arrives via local creation or socket reception.
  2. Buffer verifies that messageId is not a duplicate.
  3. Buffer verifies remaining TTL is positive.
  4. Buffer checks capacity (10 MB cap) and commits message.
  5. Querying the buffer triggers automatic purging of expired messages.

4.3.3 Functional Requirements

  • FR-4.3.1: The system shall strictly enforce a 10 MB ($10,485,760$ bytes) upper storage boundary.
  • FR-4.3.2: The system shall reject duplicate messages possessing an identical messageId.
  • FR-4.3.3: The system shall calculate $\text{remainingTTL} = \text{expiresAt} - \text{now}$ and purge expired entries automatically.

4.4 Dynamic Routing Engine (Epidemic, Spray-and-Wait, Adaptive Utility)

4.4.1 Description and Priority

Selects which messages to forward across an active encounter based on the active strategy. Priority: High.

4.4.2 Stimulus/Response Sequences

  1. Encounter begins with remote peer $P$.
  2. Routing engine queries active strategy with candidate messages.
  3. Under Epidemic, all unreceived messages are forwarded.
  4. Under Spray-and-Wait, copy tokens are halved until $L=1$.
  5. Under Adaptive, candidates are ranked by multi-metric utility score $U(M)$.

4.4.3 Functional Requirements

  • FR-4.4.1: The system shall support runtime switching between Epidemic, Spray-and-Wait, and Adaptive routing.
  • FR-4.4.2: In Spray-and-Wait, messages with $L > 1$ tokens shall split tokens binary ($\lfloor L/2 \rfloor$ sent, $\lceil L/2 \rceil$ kept); messages with $L = 1$ shall forward only to final destination.
  • FR-4.4.3: In Adaptive routing, utility shall be calculated as $U(M) = w_P \cdot P(M) + w_T \cdot T(M) + w_B \cdot B(M)$, where $w_P + w_T + w_B = 1.00$.

4.5 Multi-Transport Message Dispatch & Socket Streaming (TCP)

4.5.1 Description and Priority

Transfers DTN messages over physical Wi-Fi TCP sockets using stream-safe framing. Priority: High.

4.5.2 Stimulus/Response Sequences

  1. Routing engine designates message for dispatch.
  2. Socket connects to remote peer IP and port.
  3. System prepends a 4-byte big-endian length prefix.
  4. System writes serialized UTF-8 JSON payload bytes.
  5. Remote receiver reads exact length via readFully().

4.5.3 Functional Requirements

  • FR-4.5.1: The system shall frame all TCP payloads with a 4-byte big-endian integer length header.
  • FR-4.5.2: Receiving sockets shall ingest the exact stream length indicated by the header.

4.6 Bluetooth Low Energy GATT MTU Chunking & CRC32 Reassembly

4.6.1 Description and Priority

Slices messages into MTU-compliant BLE GATT packets and reassembles them with CRC32 verification. Priority: High.

4.6.2 Stimulus/Response Sequences

  1. Payload is partitioned into chunk payloads of size $\text{MTU} - 13$.
  2. 13-byte headers containing Transfer ID, Chunk Index, and CRC32 are prepended.
  3. Chunks are transmitted sequentially over Characteristic 0000FE62.
  4. Receiver reassembles chunks and verifies CRC32 checksum before buffer ingestion.

4.6.3 Functional Requirements

  • FR-4.6.1: The system shall attach a 13-byte header to every BLE chunk (magic bytes 0x43 0x4D, version 0x02, TxID, Index, Total, CRC32).
  • FR-4.6.2: The receiver shall verify end-to-end CRC32 checksums, rejecting corrupted transmissions.

5 Other Nonfunctional Requirements

5.1 Performance Requirements

  • Buffer Latency: Message buffer queries, insertions, and duplicate checks shall complete within 5 ms for up to 1,000 entries.
  • Adaptive Calculation Speed: Ranking 100 candidate messages in the decision matrix shall complete in under 2 ms.
  • Socket Throughput: TCP length-prefixed streaming over Wi-Fi shall achieve up to 10 MB/s transfer speeds.
  • BLE Slicing Latency: Chunking a 10 KB payload with CRC32 computation shall take less than 20 ms.

5.2 Safety Requirements

  • Memory Safety: Strict 10 MB buffer capacity prevents JVM heap exhaustion.
  • Loop Prevention: Spray-and-Wait token splitting guarantees finite replication, avoiding infinite broadcast loops.

5.3 Security Requirements

  • Payload Integrity: CRC32 checksums verify data integrity across lossy radio links.
  • Stream Protection: 4-byte length prefixes prevent TCP boundary injection attacks.
  • Zero Telemetry: No user data or telemetry is leaked to external internet entities.

5.4 Software Quality Attributes

  • Usability: Intuitive web dashboard requiring no technical terminal knowledge.
  • Reliability: Graceful socket timeout recovery; unsent messages remain buffered for subsequent encounters.
  • Maintainability: Clean modular architecture separating routing, transport, buffer, discovery, and logging.
  • Portability: Identical execution across Windows, Linux, Android, and iOS.

5.5 Business Rules

  • BR-1: Spray-and-Wait messages with $L=1$ token shall only be delivered to their final destination node.
  • BR-2: Expired messages ($\text{remainingTTL} \le 0$) shall never be forwarded or accepted.
  • BR-3: Adaptive routing weights must strictly sum to unity ($w_P + w_T + w_B = 1.00$).

6 Other Requirements

The system provides SQLite audit log export to JSON/CSV, a buffer reset option, WCAG 2.1 Level AA color contrast compliance, and full academic satisfaction for the SPIT Mini Project curriculum.

Use Case 1: Autonomous Peer Discovery via Wi-Fi Beacon
